# Laboratorio 4 · CD: la API en Hugging Face Spaces

Sábado del fin de semana 2 · 75 min · por equipos · hito E4

## Objetivo
Que un merge despliegue la API en una URL pública, sin pasos manuales. Casi todo se hace desde las páginas de Hugging Face y GitHub; solo el paso 5 usa la terminal.

Hace falta tener el [laboratorio 1](01-dagshub.md) (DagsHub) y el [laboratorio 2](02-api-docker.md) (Docker).

## Pasos

### 1. Crear el Space y el token (una persona)
1. Creen una cuenta en https://huggingface.co. Una cuenta por equipo basta.
2. Pulsen **New Space**. Nombre: `api-<equipo>`. En **SDK** elijan **Docker** y luego **Blank**. Dejen el hardware gratis y la visibilidad pública, y pulsen **Create Space**.
3. Vayan a la foto de perfil **› Settings › Access Tokens › Create new token**, elijan el tipo **Write** y copien el token.

### 2. Guardar los secretos en GitHub
En el repositorio del equipo: **Settings › Secrets and variables › Actions › New repository secret**. Creen tres:
1. `HF_TOKEN`: el token de Hugging Face.
2. `DAGSHUB_USER`: el usuario de DagsHub.
3. `DAGSHUB_TOKEN`: el token de DagsHub.

Un token subido a Git queda en el historial aunque lo borren después. Si se filtra uno, revóquenlo y creen otro.

### 3. Agregar el encabezado del Space
1. En **Code**, abran el menú de ramas, elijan `entrega/e4`, escriban `feat/cd-space` y pulsen **Create branch**.
2. Pulsen **Add file › Create new file** y en el nombre escriban `space/README.md`.
3. Peguen este contenido, que también está en [la plantilla](https://github.com/srobles5/mlops-plantilla/blob/master/space/README.md):
```markdown
---
title: API del equipo
sdk: docker
app_port: 8000
---
```
4. Pulsen **Commit changes...** y confirmen en esta rama.

Hugging Face espera por defecto el puerto 7860; `app_port` le dice que la API usa el 8000.

### 4. Agregar el workflow
1. En `feat/cd-space`, pulsen otra vez **Add file › Create new file** y en el nombre escriban `.github/workflows/cd.yml`.
2. Peguen este contenido, que también está en [la plantilla](https://github.com/srobles5/mlops-plantilla/blob/master/labs/FDS2/workflows/cd.yml), y cambien `usuario/api-equipo` por su Space:
```yaml
name: CD
on:
  push:
    branches: [master, entrega/e4]
jobs:
  desplegar:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v5
      - uses: actions/setup-python@v6
        with:
          python-version: "3.12"
      - run: pip install dvc huggingface_hub
      - name: Traer el modelo
        run: |
          dvc remote modify dagshub --local auth basic
          dvc remote modify dagshub --local user ${{ secrets.DAGSHUB_USER }}
          dvc remote modify dagshub --local password ${{ secrets.DAGSHUB_TOKEN }}
          dvc pull models/model.pkl
      - name: Subir al Space
        run: |
          cp -r api models Dockerfile requirements-api.txt space/
          hf upload usuario/api-equipo space . --repo-type=space --token=${{ secrets.HF_TOKEN }}
```
3. Pulsen **Commit changes...** y confirmen en esta rama.

`entrega/e4` está en la lista para poder probar el despliegue antes de que el docente una el E4 a `master`. Cuando el E4 se una, pueden quitarla.

### 5. Confirmar que el modelo está en DagsHub (terminal)
El modelo no está en Git: el workflow lo trae de DagsHub. Quien entrenó el último modelo corre esto en su portátil, en la rama del equipo que tenga el último `dvc.lock`:
```bash
dvc push
```
Si responde que todo está al día, ya pueden seguir.

### 6. Pull Request y despliegue
1. Pulsen **Compare & pull request**, con `base: entrega/e4` ← `compare: feat/cd-space`, y creen el PR.
2. Cuando el check `pruebas` esté en verde, otro integrante aprueba: **Files changed › Review changes › Approve › Submit review**.
3. **Merge pull request › Confirm merge**. Ese merge dispara el CD.
4. En la pestaña **Actions**, abran el workflow **CD** y esperen a que quede en verde.
5. En la página del Space, abran **Logs**: ahí Hugging Face construye la imagen. Tarda unos minutos.

### 7. Probar la URL pública
En el navegador abran estas direcciones, en minúsculas:
```text
https://<usuario>-api-<equipo>.hf.space/health
https://<usuario>-api-<equipo>.hf.space/docs
```
En `/docs`, prueben `/predict` con **Try it out › Execute**. Un Space gratis se duerme si nadie lo usa: la primera petición puede tardar.

### 8. Comprobar que se actualiza solo
1. Desde `entrega/e4`, creen una rama nueva con el menú de ramas.
2. Abran `api/app.py`, pulsen el lápiz (**Edit this file**), cambien el `title` de `FastAPI` y pulsen **Commit changes...**.
3. Abran el PR hacia `entrega/e4`. Otro integrante aprueba y hace el merge.
4. Cuando termine la construcción, recarguen `/docs`: debe aparecer el título nuevo.

### 9. Entrega del E4
El E4 se termina en el taller del viernes del fin de semana 3. Cuando el checklist de [docs/entregas.md](https://github.com/srobles5/mlops-plantilla/blob/master/docs/entregas.md) esté completo, abran el PR con `base: master` ← `compare: entrega/e4`.

## Listo cuando
- [ ] La URL pública responde en `/health`.
- [ ] `/predict` da una predicción desde esa URL.
- [ ] Los tokens están en GitHub Secrets y en ningún archivo.
- [ ] Un merge actualizó la API sin pasos manuales.

## Errores frecuentes
- **`Unable to find the remote` o `config file error` en `dvc remote modify`**: el remote no se llama `dagshub` en `.dvc/config`, o ese cambio no está en la rama.
- **`failed to pull data from the cloud`**: falta `dvc push` de quien entrenó, o `DAGSHUB_USER` y `DAGSHUB_TOKEN` están mal.
- **`401` o `403` en `hf upload`**: el token no es de tipo Write, o el Space no es de esa cuenta.
- **`404` o `Repository Not Found` en `hf upload`**: no han creado el Space o el nombre no coincide.
- **El Space queda en `Configuration error`**: `space/README.md` no empieza con el encabezado entre `---`, o falta `sdk: docker`.
- **El Space queda en `Starting` y nunca abre**: `app_port` no coincide con el puerto del `CMD`.
- **`Permission denied` en los logs del Space**: el contenedor corre con el usuario 1000. La API no debe escribir archivos dentro de `/app`.
- **Hugging Face falla ese día**: Render, en su plan gratis, sirve de respaldo con el mismo Dockerfile.
