# Laboratorio 3 · CI: pruebas en cada Pull Request

Sábado del fin de semana 2 · 85 min · por equipos · hito E4

## Objetivo
Que cada Pull Request se pruebe solo y que GitHub no deje unir uno que falla.

## Pasos

### 0. Ramas
Con el E3 ya unido a `master`, creen la rama de entrega. Si el E3 sigue pendiente, salgan de `entrega/e3`.
```bash
git switch master
git pull
git switch -c entrega/e4
git push -u origin entrega/e4
git switch -c feat/ci-pruebas
```

### 1. Pruebas de la API
Creen `tests/test_api.py`. Las pruebas no necesitan el dataset: entrenan un modelo de juguete en segundos, porque prueban la API y no la calidad del modelo.
```python
import importlib
import sys
from pathlib import Path

import joblib
import pandas as pd
import pytest
from fastapi.testclient import TestClient
from sklearn.linear_model import LogisticRegression

sys.path.insert(0, str(Path(__file__).resolve().parents[1]))


@pytest.fixture()
def client(tmp_path, monkeypatch):
    X = pd.DataFrame({"tenure": [1, 60], "MonthlyCharges": [90, 20]})
    joblib.dump(LogisticRegression().fit(X, ["Yes", "No"]), tmp_path / "model.pkl")
    monkeypatch.setenv("MODEL_DIR", str(tmp_path))
    import api.app as modulo
    importlib.reload(modulo)
    return TestClient(modulo.app)


def test_health(client):
    assert client.get("/health").json() == {"status": "ok"}


def test_predict(client):
    r = client.post("/predict", json={"tenure": 2})
    assert r.status_code == 200
    assert r.json()["prediccion"] in {"Yes", "No"}


def test_dato_invalido(client):
    assert client.post("/predict", json={"tenure": "muchos"}).status_code == 422
```
Adáptenlas a su dataset: cambien `tenure` y `MonthlyCharges` por dos columnas numéricas de `Cliente`, y `Yes` y `No` por sus clases. En regresión, cambien `LogisticRegression` por `LinearRegression` y `["Yes", "No"]` por dos números, y comprueben solo que `"prediccion"` esté en la respuesta.

```bash
pip install ruff
pytest -q
ruff check api tests
```

### 2. El workflow
Creen `.github/workflows/ci.yml`:
```yaml
name: CI
on:
  pull_request:
jobs:
  pruebas:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v5
      - uses: actions/setup-python@v6
        with:
          python-version: "3.12"
      - run: pip install -r requirements-api.txt ruff
      - run: ruff check api tests
      - run: pytest -q
```

### 3. Abrir el PR y leer el resultado
```bash
git add tests .github/workflows/ci.yml
git commit -m "Agrega pruebas y CI"
git push -u origin feat/ci-pruebas
```
PR con `base: entrega/e4` ← `compare: feat/ci-pruebas`. Abran la pestaña **Actions** y lean cada paso, de arriba abajo.

### 4. Exigir el check
Cuando el workflow haya corrido, una persona entra a **Settings › Branches** y edita las reglas de `master` y de `entrega/*`: **Require status checks to pass before merging**, busca `pruebas` y guarda. El check solo aparece en la lista después de haber corrido una vez.

Otro integrante aprueba y hace el merge del PR.

### 5. Comprobar el bloqueo
```bash
git switch entrega/e4
git pull
git switch -c fix/prueba-rojo
```
Rompan algo a propósito: en `api/app.py`, cambien `"ok"` por `"mal"` en `/health`. Hagan commit, push y un PR hacia `entrega/e4`. Debe quedar en rojo y con el botón de merge bloqueado. Cierren el PR sin unirlo y borren la rama.

## Errores frecuentes
- **`ModuleNotFoundError: No module named 'httpx'`** o **`pytest: command not found`**: faltan en `requirements-api.txt`.
- **El workflow no aparece en Actions**: el archivo no está en `.github/workflows/` o la extensión no es `.yml`.
- **Error de sangría en el YAML**: se usan espacios, nunca tabulaciones.
- **El check no aparece en la regla de la rama**: el workflow todavía no ha corrido, o corrió con otro nombre de job.
- **`F401` con `imported but unused`**: `ruff` encontró un import sin usar. Bórrenlo.
- **Pasa en mi portátil y falla en Actions**: falta una dependencia en `requirements-api.txt`. Esa máquina está limpia: justamente por eso se prueba ahí.
