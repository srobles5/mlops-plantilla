# Laboratorio 3 · CI: pruebas en cada Pull Request

Sábado del fin de semana 2 · 85 min · por equipos · hito E4

## Objetivo
Que cada Pull Request se pruebe solo y que GitHub no deje unir uno que falla. Todo se hace desde la página de GitHub, en el repositorio del equipo: no hace falta la terminal.

## Pasos

### 1. Crear las ramas
1. En la pestaña **Code**, abran el menú de ramas (dice `master`).
2. Escriban `entrega/e4` y pulsen **Create branch entrega/e4 from master**. Si el E3 sigue pendiente, elijan primero `entrega/e3` en ese menú, para partir de ahí.
3. Ya en `entrega/e4`, abran otra vez el menú, escriban `feat/ci-pruebas` y pulsen **Create branch**.

Revisen que el menú diga `feat/ci-pruebas`: ahí va todo lo de los pasos 2 y 3.

### 2. Agregar las pruebas
1. Pulsen **Add file › Create new file**.
2. En el nombre escriban `tests/test_api.py`. La barra `/` crea la carpeta.
3. Peguen este código, que también está en [la plantilla](https://github.com/srobles5/mlops-plantilla/blob/master/tests/test_api.py):
```python
import importlib
import sys
from pathlib import Path

import joblib
import pandas as pd
import pytest
from fastapi.testclient import TestClient
from sklearn.linear_model import LogisticRegression

sys.path.insert(0, str(Path(__file__).resolve().parents[1]))


@pytest.fixture()
def client(tmp_path, monkeypatch):
    X = pd.DataFrame({"tenure": [1, 60], "MonthlyCharges": [90, 20]})
    joblib.dump(LogisticRegression().fit(X, ["Yes", "No"]), tmp_path / "model.pkl")
    monkeypatch.setenv("MODEL_DIR", str(tmp_path))
    import api.app as modulo
    importlib.reload(modulo)
    return TestClient(modulo.app)


def test_health(client):
    assert client.get("/health").json() == {"status": "ok"}


def test_predict(client):
    r = client.post("/predict", json={"tenure": 2})
    assert r.status_code == 200
    assert r.json()["prediccion"] in {"Yes", "No"}


def test_dato_invalido(client):
    assert client.post("/predict", json={"tenure": "muchos"}).status_code == 422
```
4. Adáptenlo a su dataset: cambien `tenure` y `MonthlyCharges` por dos columnas numéricas de `Cliente`, y `Yes` y `No` por sus clases. En regresión, cambien `LogisticRegression` por `LinearRegression` y `["Yes", "No"]` por dos números, y comprueben solo que `"prediccion"` esté en la respuesta.
5. Pulsen **Commit changes...**, dejen marcado **Commit directly to the feat/ci-pruebas branch** y confirmen con **Commit changes**.

Las pruebas no necesitan el dataset: entrenan un modelo de juguete en segundos, porque prueban la API y no la calidad del modelo.

### 3. Agregar el workflow
1. En `feat/ci-pruebas`, pulsen otra vez **Add file › Create new file**.
2. En el nombre escriban `.github/workflows/ci.yml`.
3. Peguen este contenido sin cambios, que también está en [la plantilla](https://github.com/srobles5/mlops-plantilla/blob/master/labs/FDS2/workflows/ci.yml):
```yaml
name: CI
on:
  pull_request:
jobs:
  pruebas:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v5
      - uses: actions/setup-python@v6
        with:
          python-version: "3.12"
      - run: pip install -r requirements-api.txt ruff
      - run: ruff check api tests
      - run: pytest -q
```
4. Pulsen **Commit changes...** y confirmen en la misma rama.

### 4. Abrir el PR y leer el resultado
1. Pulsen **Compare & pull request**. Si no aparece, vayan a **Pull requests › New pull request**.
2. Elijan `base: entrega/e4` ← `compare: feat/ci-pruebas`.
3. Borren la plantilla de entrega, escriban qué cambia y pulsen **Create pull request**.
4. Al final del PR aparece el check `pruebas`. Pulsen **Details** y lean cada paso, de arriba abajo.

Si queda en rojo, corrijan el archivo en esta misma rama con el lápiz (**Edit this file**): el PR se vuelve a probar solo.

### 5. Exigir el check
Cuando el workflow haya corrido, una persona hace esto:
1. Vayan a **Settings › Branches** y pulsen **Edit** en la regla de `master`.
2. Marquen **Require status checks to pass before merging**.
3. En el buscador escriban `pruebas`, selecciónenlo y pulsen **Save changes**.
4. Repitan con la regla de `entrega/*`.

Después, otro integrante revisa el PR: **Files changed › Review changes › Approve › Submit review**. Luego **Merge pull request › Confirm merge** y **Delete branch**.

### 6. Comprobar el bloqueo
1. Abran el menú de ramas, elijan `entrega/e4`, escriban `fix/prueba-rojo` y pulsen **Create branch**.
2. Abran `api/app.py` y pulsen el lápiz (**Edit this file**).
3. En `/health`, cambien `"ok"` por `"mal"` y pulsen **Commit changes...** en esta rama.
4. Abran un PR con `base: entrega/e4` ← `compare: fix/prueba-rojo`. Debe quedar en rojo y con el botón de merge bloqueado.
5. Pulsen **Details** y busquen al final qué prueba falló y por qué.
6. Pulsen **Close pull request** y **Delete branch**.

### Opcional: probar en su portátil
Antes de subir un cambio, las mismas pruebas se pueden correr en la terminal:
```bash
pip install ruff
pytest -q
ruff check api tests
```

- [ ] Un PR en rojo no se puede unir.
- [ ] Todo el equipo leyó un error en Actions.

## Errores frecuentes
- **`ModuleNotFoundError: No module named 'httpx'`** o **`pytest: command not found`**: faltan en `requirements-api.txt`.
- **`No such file or directory: 'requirements-api.txt'`** o **`No module named 'api'`**: la rama no salió de una que ya tenga el E3.
- **El workflow no aparece en Actions**: el archivo no está en `.github/workflows/` o la extensión no es `.yml`.
- **Error de sangría en el YAML**: se usan espacios, nunca tabulaciones.
- **El check no aparece en la regla de la rama**: el workflow todavía no ha corrido, o corrió con otro nombre de job.
- **`F401` con `imported but unused`**: `ruff` encontró un import sin usar. Bórrenlo.
- **Quedó un archivo en otra rama**: el menú de ramas no decía `feat/ci-pruebas` al crearlo. Revisen ese menú antes de cada commit.
